## 3. АРХИТЕКТУРА ПРИЛОЖЕНИЯ

Соблюдай существующую модульную структуру:

* `pwa/models/` — модели данных и типизированные структуры.
* `pwa/state/` — бизнес-логика, состояние Reflex, события и вычисляемые свойства.
* `pwa/ui/components/` — переиспользуемые UI-компоненты.
* `pwa/ui/pages/` — страницы и регистрация маршрутов.
* `pwa/pwa.py` — точка входа приложения.

### 3.1. Модели

Для ORM-моделей SQLAlchemy:

* Явно указывай схему PostgreSQL через `__table_args__ = {"schema": "..."}`, если модель действительно соответствует таблице в этой схеме.
* Соблюдай фактические имена таблиц и столбцов.
* Учитывай первичные и внешние ключи, уникальность, `NULL`, значения по умолчанию и типы данных.
* Не создавай ORM-модели для существующих таблиц вслепую: сначала проверь их реальную структуру.
* Не смешивай ORM-модели базы данных с моделями передачи данных в интерфейс.

Для данных, передаваемых в состояние Reflex, используй подходящие типизированные структуры, например Pydantic-модели. Не передавай в состояние произвольные объекты SQLAlchemy, соединения, курсоры или другие объекты, которые нельзя безопасно сериализовать.

### 3.2. Бизнес-логика

В `pwa/state/` размещай:

* загрузку и подготовку данных;
* валидацию пользовательского ввода;
* бизнес-правила;
* операции чтения и записи;
* обработку ошибок;
* события Reflex;
* вычисляемые свойства состояния.

UI-компоненты не должны самостоятельно выполнять SQL-запросы или реализовывать бизнес-правила.

### 3.3. UI-компоненты

В `pwa/ui/components/` размещай:

* таблицы;
* панели инструментов;
* формы редактирования;
* фильтры и поиск;
* модальные окна;
* отображение метаданных;
* переиспользуемые элементы управления.

Компоненты должны получать данные из состояния и передавать пользовательские действия в обработчики состояния.

### 3.4. Страницы

Каждая страница должна иметь собственный маршрут и быть оформлена декорированной функцией.

Пример:

```python
@rx.page(route="/my-route", on_load=MyState.load_data)
def my_page() -> rx.Component:
    return rx.container(my_component())
```

Импорт страницы в `pwa.py` должен обеспечивать её регистрацию в соответствии с принятой архитектурой приложения.

Не используй `app.add_page()` как альтернативный механизм регистрации, если проект придерживается схемы с `@rx.page`.

В `pwa/pwa.py` оставляй только необходимую инициализацию приложения и импорты страниц. Не размещай там бизнес-логику.

## 4. НЕСКОЛЬКО НЕЗАВИСИМЫХ БАЗ ДАННЫХ

В приложении могут одновременно использоваться базы `ledger` и `household`.

Каждая база имеет собственное подключение, транзакции и жизненный цикл соединений.

### 4.1. Подключения

Используй существующие объекты подключения, например `engine` и `household_engine`, если именно так они определены в проекте.

Не создавай новые движки, сессии или механизмы подключения без необходимости.

При работе с SQL:

```python
from sqlalchemy import text

with engine.connect() as conn:
    result = conn.execute(text("""
        SELECT id, slug, title
        FROM projects.registry
    """))
    rows = result.mappings().all()
```

Используй соответствующий движок для каждой базы.

Обеспечивай корректное закрытие соединений через контекстные менеджеры. Для записи явно управляй транзакциями, используя подходящий механизм SQLAlchemy, например `engine.begin()`.

Не передавай соединения или результаты запросов непосредственно в состояние Reflex.

### 4.2. Владение данными

До реализации операции определи:

* какая база является источником данных;
* какая таблица владеет каждым полем;
* какой идентификатор связывает записи;
* где разрешено изменение данных;
* как согласуются данные, полученные из разных баз.

Не считай, что одинаковые названия таблиц, схем или столбцов в двух базах означают одинаковую структуру или семантику.

### 4.3. Запись в несколько баз

Не предполагай, что обычная транзакция SQLAlchemy обеспечивает атомарность операций сразу в двух независимых базах.

Если операция изменяет обе базы:

1. Определи порядок записи и возможные точки отказа.
2. Предусмотри обработку частичного успеха.
3. При необходимости используй повторяемые операции, журнал изменений, механизм компенсации или иной явно описанный способ восстановления.
4. Не сообщай об успешном сохранении всего изменения, если подтверждена запись только в одну базу.

Не внедряй распределённые транзакции без доказанной необходимости.

## 5. КРОСС-БАЗОВЫЙ IN-MEMORY JOIN

Если базы не объединены на уровне PostgreSQL, выполняй логическое объединение данных в Python.

Основной подход:

1. Получить необходимые записи из первой базы.
2. Получить необходимые записи из второй базы.
3. Построить словарь по общему идентификатору.
4. Объединить записи в памяти.
5. Преобразовать результат в типизированные структуры, предназначенные для интерфейса.

Пример:

```python
metadata_by_id = {
    str(row["project_id"]): row
    for row in metadata_rows
}

combined = []

for project in registry_rows:
    project_id = str(project["id"])
    metadata = metadata_by_id.get(project_id)

    combined.append({
        "id": project_id,
        "slug": project["slug"],
        "title": project["title"],
        "meta": metadata["meta"] if metadata else {},
    })
```

Это иллюстративный пример. Используй реальные идентификаторы и поля проекта, предварительно проверив их структуру.

### 5.1. Сложность и объём данных

При построении хэш-индекса и одном проходе по каждой коллекции ожидаемая временная сложность объединения составляет O(N + M), где N и M — количество записей в источниках.

Не загружай большие таблицы целиком только ради простоты реализации.

При росте объёма данных оцени необходимость:

* фильтрации на стороне PostgreSQL;
* ограничения количества полей в запросе;
* пагинации;
* постраничной загрузки;
* ограничения объёма JSONB;
* индексов по полям поиска;
* кеширования, если оно согласуется с требованиями актуальности данных.

Не объединяй данные только по отображаемому названию или `slug`, если предусмотрен устойчивый идентификатор.

Учитывай возможное отсутствие связанных записей, дублирование идентификаторов и различия типов UUID и строк. Нормализуй ключи последовательно.

## 6. REFLEX: СОСТОЯНИЕ, РЕАКТИВНОСТЬ И РЕНДЕРИНГ

### 6.1. Типизированное состояние

Не используй сырые списки словарей как основной контракт данных между серверной логикой и UI.

Для коллекций, отображаемых через `rx.foreach`, предпочитай типизированные структуры, например:

```python
from pydantic import BaseModel


class ProjectItem(BaseModel):
    id: str
    slug: str
    title: str
    status: str
    meta: dict = {}
```

Это лишь базовый пример. Подбирай поля, типы и значения по фактической модели данных.

Не используй изменяемые значения по умолчанию без понимания поведения выбранного механизма типизации. Для сложных полей при необходимости используй `Field(default_factory=dict)`.

### 6.2. Начальное состояние и пустые коллекции

Явно определяй начальное состояние коллекций, чтобы первый рендеринг не зависел от того, успели ли загрузиться данные.

Различай состояния:

* данные ещё загружаются;
* данные успешно загружены, но коллекция пуста;
* произошла ошибка загрузки;
* данные загружены успешно.

Не показывай бесконечный текст «Загрузка...», если загрузка уже завершилась с пустым результатом или ошибкой.

Защищай отображение от отсутствующих значений и необязательных полей. Проверяй точный API установленной версии Reflex и корректность выражений в `rx.cond`, `rx.foreach` и вычисляемых свойствах.

Не считай условие `collection.length() > 0` универсальным решением для всех ситуаций: тип коллекции, её начальное значение и поведение при сериализации должны быть проверены в контексте проекта.

### 6.3. События

Используй существующую модель событий Reflex.

* События чтения и записи должны быть явно отделены от вычисляемых свойств.
* Не выполняй SQL-запросы при каждом рендеринге компонента.
* Не запускай запись в базу из вычисляемого свойства.
* Обеспечивай обработку исключений и понятную обратную связь пользователю.
* При длительных операциях предотвращай неконтролируемые повторные запросы и дублирование записей.
* Учитывай, что состояние Reflex может быть сериализовано и обновляться в рамках событий.

Перед использованием новых возможностей фреймворка сверяйся с версией Reflex, закреплённой в проекте. Не придумывай названия API и не переносись автоматически на синтаксис другой версии.

## 7. JSONB: ЧТЕНИЕ, ВАЛИДАЦИЯ И СОХРАНЕНИЕ

Поле `meta` предназначено для структурированных, потенциально нерегулярных метаданных.

### 7.1. Чтение

Учитывай, что данные JSONB могут быть:

* объектом;
* массивом;
* строкой, числом или логическим значением;
* `null`;
* отсутствующими в результирующей записи.

Если приложение ожидает JSON-объект, явно проверяй его тип и обрабатывай несовместимые значения.

Не полагайся на `json.loads()` без проверки: драйвер PostgreSQL может уже возвращать JSONB как Python-объект. Не выполняй повторный разбор уже декодированного словаря.

### 7.2. Отображение

Для просмотра метаданных используй подходящий компонент, например модальное окно с таблицей ключей и значений.

При необходимости корректно отображай вложенные объекты и массивы. Не предполагай, что все значения JSONB являются простыми строками.

### 7.3. Редактирование

Для редактирования можно использовать текстовое поле с JSON-представлением либо структурированную форму.

При текстовом редактировании:

1. Сохраняй исходное значение до начала редактирования.
2. Проверяй синтаксис JSON до записи.
3. Проверяй, что корневой тип соответствует требованиям поля.
4. Выполняй предметную валидацию известных ключей, если она предусмотрена.
5. При ошибке показывай сообщение и сохраняй возможность исправить ввод.
6. Не записывай невалидный JSON в базу.
7. Не заменяй исходные метаданные пустым объектом только потому, что парсинг завершился ошибкой.

Для SQLAlchemy `text()` не используй неоднозначный синтаксис приведения вида `:meta::jsonb`. Применяй явный SQL `CAST(:meta AS jsonb)` с параметризованным запросом:

```python
stmt = text("""
    UPDATE projects.metadata
    SET meta = CAST(:meta AS jsonb)
    WHERE project_id = :project_id
""")
```

Передавай `meta` и `project_id` через параметры запроса. Не формируй SQL конкатенацией пользовательских значений.

Проверяй число затронутых строк. Если запись не найдена или обновление не выполнено, не сообщай об успехе.

### 7.4. Сохранность данных

При редактировании нерегулярных метаданных не удаляй неизвестные ключи без явного требования.

Если одновременно возможны изменения записи несколькими пользователями или процессами, оцени необходимость контроля конкурентного обновления — например, по версии записи или исходному значению.

Не вводи новую схему метаданных без оценки совместимости с существующими данными.

## 8. СПРАВОЧНИКИ И СТАТУСЫ

Значения, управляемые справочниками, должны загружаться из соответствующих таблиц PostgreSQL, если справочник уже существует.

Например, при загрузке статусов проектов:

```sql
SELECT ...
FROM dicts.dict_statuses
WHERE entity_type = 'PROJECT'
```

Используй реальные столбцы таблицы, подтверждённые схемой базы данных.

Обязательно:

* фильтруй справочник по правильному контексту;
* не смешивай статусы разных типов сущностей;
* не хардкодь значения, если источник истины — база данных;
* корректно обрабатывай отсутствие активных значений;
* проверяй, что выбранный статус допустим для редактируемой сущности;
* не изменяй смысл существующих статусов ради удобства UI.

Если в системе есть отдельные идентификаторы статуса и его отображаемое название, сохраняй идентификатор, а название используй для интерфейса.

## 9. ПОИСК, ФИЛЬТРЫ И ТАБЛИЦЫ

Для модулей с большим количеством записей предусматривай управляемый поиск и фильтрацию.

При реализации:

* ищи только по предусмотренным полям;
* корректно обрабатывай пустую строку и пробелы;
* используй debounce для уменьшения количества запросов или пересчётов, когда это уместно;
* не смешивай фильтрацию интерфейса с изменением исходных данных;
* обеспечивай устойчивую идентификацию строк;
* не используй индекс строки как идентификатор записи;
* сохраняй выбранные фильтры в рамках ожидаемого жизненного цикла состояния.

Если используется debounce, убедись, что выбранный механизм совместим с Reflex и не приводит к выполнению устаревших запросов после более нового ввода.

* право подключения к соответствующей базе;

Пользовательский ввод всегда передавай как параметры SQL. Не собирай запросы путём вставки пользовательских строк.

Разделяй техническую диагностику и сообщения пользователю.

Не показывай пользователю секреты, строки подключения или внутренние детали исключений. При этом сохраняй достаточную диагностическую информацию в логах, следуя принятой в проекте системе логирования.

Не скрывай исключения так, чтобы система сообщала об успешной операции при фактической ошибке.

## 12. ПРОИЗВОДИТЕЛЬНОСТЬ И МАСШТАБИРОВАНИЕ

Перед оптимизацией определяй фактическое узкое место.

Учитывай:

* количество SQL-запросов;
* объём считываемых данных;
* стоимость преобразования JSONB;
* сложность объединения в памяти;
* частоту событий Reflex;
* объём данных, передаваемых клиенту;
* повторную загрузку справочников;
* необходимость индексов и пагинации.

Не добавляй кеширование, фоновые задачи или новые слои абстракции без обоснования.

Не жертвуй корректностью данных ради сокращения числа строк кода или запросов.

## 13. ТЕСТИРОВАНИЕ И ПРОВЕРКА

Каждый новый модуль должен иметь понятный план проверки.

Минимально проверяй:

1. Успешную загрузку данных из каждой базы.
2. Корректность объединения связанных записей.
3. Поведение при отсутствии связанных данных.
4. Пустые коллекции и начальное состояние UI.
5. Корректность фильтров и поиска.
6. Загрузку справочников с необходимой фильтрацией.
7. Сохранение валидных JSONB-метаданных.
8. Отказ при невалидном JSON.
9. Ошибки записи и недоступность базы.
10. Проверку маршрута и интеграции с приложением.

Если в проекте существуют тесты, расширяй существующую систему тестирования, а не создавай параллельный механизм без необходимости.

Перед завершением:

* проверь синтаксис изменённых Python-файлов;
* запусти доступные релевантные тесты;
* проверь, что страница регистрируется;
* проверь импорты и связи модулей;
* проверь `git diff`;
* убедись, что нет непреднамеренных изменений.

Не утверждай, что тесты прошли, если они не запускались. Разделяй выполненные проверки, предполагаемые проверки и то, что осталось проверить вручную.

## 14. РАБОТА С GIT И РЕЕСТРОМ РАЗВИТИЯ

При изменении проекта соблюдай существующий стиль Git-коммитов и ведения реестра обновлений.

Перед коммитом:

1. Проверь `git status`.
2. Изучи изменённые и новые файлы.
3. Убедись, что удаления ожидаемы.
4. Просмотри `git diff` и при необходимости `git diff --cached`.
5. Не включай посторонние пользовательские изменения.
6. Используй согласованный формат сообщения коммита.

Если в проекте есть реестр обновлений, например UVR, подготовь запись в принятом формате. Не выдумывай структуру таблицы, идентификаторы версии, номера обновлений или обязательные поля: проверь существующие записи и схему.

Не выполняй коммит автоматически, если пользователь просил только подготовить изменения или проверить код.

Не сообщай об успешном коммите, выполнении SQL или изменении файлов, если фактически это не было выполнено.

## 15. ПОРЯДОК ВЫПОЛНЕНИЯ ЗАДАЧИ

Для каждого нового модуля или существенного изменения работай по следующему алгоритму.

### Этап A. Исследование

* Изучи существующую структуру.
* Найди аналогичные реализации.
* Проверь реальные схемы БД и модели.
* Определи затрагиваемые файлы и зависимости.

### Этап B. Проектирование

Кратко зафиксируй:

* цель изменения;
* источники данных;
* владение полями;
* способ объединения данных;
* модель состояния;
* маршрут страницы;
* способ записи и обработки ошибок;
* список изменяемых файлов.

Не усложняй архитектуру без необходимости.

### Этап C. Реализация

* Соблюдай существующий стиль.
* Не дублируй уже реализованные функции.
* Не изменяй несвязанные модули.
* Не делай предположений о структуре базы без проверки.
* Сохраняй обратную совместимость там, где она требуется.

### Этап D. Проверка

* Проверь синтаксис, импорты и типы.
* Проверь основные сценарии и ошибки.
* Проверь SQL и границы транзакций.
* Проверь интеграцию страницы.
* Изучи итоговый diff.

### Этап E. Отчёт

В конце укажи:

1. Что реализовано.
2. Какие файлы изменены или созданы.
3. Какие базы, схемы и таблицы задействованы.
4. Какие проверки выполнены и с каким результатом.
5. Что осталось сделать или проверить вручную.
6. Какие решения требуют согласования.

## 16. ПРАВИЛА ИНЖЕНЕРНОГО ВЗАИМОДЕЙСТВИЯ

* Не переписывай существующий код целиком, если достаточно локального изменения.
* Не вводи новую зависимость без необходимости.
* Не подменяй реальную структуру проекта демонстрационными примерами.
* Не скрывай неопределённость.
* Не делай необратимых изменений без согласования.
* Если есть несколько решений, выбирай наиболее простое, совместимое и проверяемое.
* Если задача недостаточно определена, задай один конкретный уточняющий вопрос, который действительно влияет на реализацию. Если можно безопасно продолжить, укажи предположение и продолжай.
* Если обнаружена архитектурная проблема, объясни её и предложи минимальный путь исправления.
* Не считай задачу завершённой только потому, что код написан: учитывай интеграцию, проверку и эксплуатационное поведение.

**Итоговый принцип:** развивай не отдельный экран, а согласованную систему. Каждый новый модуль должен опираться на существующие правила, сохранять целостность данных и облегчать следующие изменения, не создавая скрытых зависимостей и не увеличивая неопределённость системы.
