* Эпоха 2 (Операции 447–1269) — Целевой диапазон текущего ТЗ: 
  Транзитный участок, характеризующийся переходом на дискретный поочередный 
  учет счетов. На отрезке 1266–1269 в исходнике содержатся системные операции 
  актуализации балансов (Ревизия).

* Эпоха 3 (Операции 1270+):

2. Целевая парадигма: Data-Driven Stateless Engine
Мы полностью отказываемся от монолитного скрипта «все в одном», перегруженного 
частными if/else костылями прошлых периодов. Скрипт превращается в «слепой 
движок», разделенный на изолированные модули:

* Код ничего не знает о конкретных номерах транзакций. Вся специфика и 
  исключения читаются динамически из СУБД (public.etl_transform_rules).
* Поток данных на Этапе 2 строго линеен. Логика раздвоения строк (SPLIT_RULE) 
  упразднена. Одна входящая строка из сырья = одна целевая запись.

3. Технические параметры инициализации (Точка старта)
Скрипт блокирует обнуление переменных и жестко инициализирует кумулятивные 
балансы и счетчики на момент закрытия 446 операции:

* Стартовый сквозной ключ (code / tr_id): 534 (продолжение после архивного 533).
* Входящее фиксированное сальдо (Snapshot на шаг 447):
  - ACC-003 (Касса): 0.00 тг
  - ACC-004 (Карман): -3990.00 тг (Исторический минус)
  - ACC-005 (Счет 1): 0.00 тг
  - ACC-006 (Счет 2): 0.00 тг
  - ACC-015 (Счет OLX): 0.00 тг

Все новые счета (Счет 3, Счет 4, Счет 7 и т.д.), впервые появляющиеся в 
потоке далее, инициализируются со стартовым балансом 0.00 тг.

4. Пошаговая структура конвейера (Объем изменений)

* Шаг №1: Экстракция данных (SQL-фильтр)
  Для полной разгрузки памяти и процессора, SQL-запрос на чтение из сырой 
  таблицы ограничивается жесткими рамками:
  
  SELECT * FROM public."transaction_registry FLW_030"
  WHERE "Код"::integer BETWEEN 447 AND 1269
  ORDER BY "Код" ASC NULLS LAST;

* Шаг №2: Изолированный блок предобработки и валидации данных
  Перед запуском математических расчетов скрипт осуществляет нормализацию:
  - Защита от NULL: Любые пропуски в поле "Сумма *" (тип numeric) на уровне 
    Python принудительно преобразуются в Decimal('0.00').
  - Динамический маппинг: Текстовые названия счетов из поля "Счет" 
    конвертируются в системные ID (ACC-XXX) на основе справочника 
    public.account_register. При обнаружении неизвестного счета скрипт 
    маркирует его для лога QA.

* Шаг №3: Чистый математический калькулятор
  Расчет кумулятивного баланса счета выполняется по формуле:
  Баланс(i+1) = Баланс(i) + (Сумма(i) * AccountEffect(TypeID))
  
  Знаки операций (AccountEffect = +1/-1) извлекаются динамически из справочника 
  public.dict_type. Расчеты ведутся через Decimal с округлением до 2 знаков.

ЧАСТЬ 2: ПОЯСНИТЕЛЬНАЯ ЗАПИСКА (МЕТАДАННЫЕ И РЕЗУЛЬТАТЫ СЕССИИ)
--------------------------------------------------------------------------------
В ходе выполнения ТЗ была совершена архитектурная эволюция. Первоначальный 
тяжелый базис из 7 типов правил, использовавшийся в Эпохе 1, был успешно 
сокращен до 2 универсальных декларативных типов (MVS - Minimal Viable Structure):
  1) MUTATE_ROW — изменение структуры/значений полей сырой строки до расчетов.
  2) INJECT_ROWS — впрыскивание полноценных виртуальных строк в поток.

Это позволило закрыть весь диапазон 447–1269 без единой правки кода ядра.

Большинство изменений связаны с неверным указанием счета транзакции, ошибками при
ручном расчете. Изменен тип "Ревизия" у всех операций на тип "Корректировка".

Итоговый результат: Полное сведение (0 дельт расхождений).

Архив является полностью изолированным и автономным. Для воспроизведения:

2) Восстановить DDL-структуру (инфраструктурные CSV-файлы метаданных не содержат
