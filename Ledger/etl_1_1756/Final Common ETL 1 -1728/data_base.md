ТЕХНИЧЕСКИЙ ПАСПОРТ: FINANCE LEDGER DATABASE

1. КОНЦЕПЦИЯ
Система двойной записи (PostgreSQL) для ведения личных финансов. 
Документ описывает структуру данных, правила ETL-процесса и регламент аудита.

2. АРХИТЕКТУРА ТАБЛИЦ

2.1. Справочники (Infrastructure)
- account_register: Список финансовых счетов.
- contragent_register: Реестр контрагентов. Ключ: cnaid (Unique).
- dict_category: Иерархия категорий. Поддерживает связи parent_category_id -> category_id.
- dict_type: Справочник типов операций. Важное поле: AccountEffect (влияние на баланс).
- entity_registry_t: Реестр юридических сущностей.

2.2. Ядро данных (Core Ledger)
- tx_register: Основная таблица транзакций.
    - Ключевые поля: code (PK), tr_sum, tr_currency, registration_date, operation_date, sql_acc_balance.
    - Аудиторские метрики: sql_python_diff, sql_manual_diff (разница между расчетными данными).

3. БИЗНЕС-ПРАВИЛА И ЛОГИКА
- Расчет баланса осуществляется через выражение balance(i+1) = balance(i)+sum(i)*AccountEffect(TypeID). Сумма операции может быть отрицательной. AccountEffect(TypeID) - множитель из справочника dict_type, определяющий направление влияния операции на баланс (обычно 1 или -1)
- Приоритет данных: sql_acc_balance является эталонным балансом.
- Валидация: Транзакция считается проблемной, если sql_python_diff != 0 или sql_manual_diff != 0.
- Целостность: Система использует "мягкие связи" (Soft Links). При SQL-запросах обязательно использование LEFT JOIN для таких полей как acc_id, ent_id, contragent_from_id.
- Защита (Security): Триггер trg_protect_verified_data блокирует UPDATE/DELETE для диапазона code 1-1821.

4. СТАТУС ИСТОРИЧЕСКОГО КОНТУРА
- Эпоха 1 (1-446): Верифицирована (ID 533).
- Эпоха 2 (447-1269): Полностью сведена (0 дельт).
- Контур (1-1821): Активная верифицированная зона.

5. РЕКОМЕНДАЦИИ ПО SQL-ЗАПРОСАМ
1. Поиск аномалий: Фильтровать по sql_python_diff != 0 или sql_manual_diff != 0.
2. Деревья категорий: Использовать WITH RECURSIVE для связи с parent_category_id.
3. Аудит: При анализе связей контрагентов всегда учитывать NULL в contragent_from_id (индикация внутреннего перевода).
