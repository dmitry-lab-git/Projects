# ТЕХНИЧЕСКОЕ ЗАДАНИЕ (BUILD SPECIFICATION)
## Модернизация транзакционного шлюза и модуля верификации системы финансового учета

---

### 1. ОБЩИЕ ТРЕБОВАНИЯ И РЕФАКТОРИНГ СХЕМЫ ДАННЫХ (UUID & UTC)

#### 1.1 Перевод таблицы `audit.staging_transactions` в формат UUID
* Полный отказ от строкового хранения внешних ключей (`varchar(50)`). Поля, содержащие суффикс `_str`, подлежат конвертации в тип `UUID` с последующим переименованием (удалением суффикса).
* Связанные таблицы отчетов (включая `reports.account_state_report.account_id`) синхронно переводятся на тип данных `UUID` для обеспечения ссылочной целостности и оптимизации индексов.

#### 1.2 Переход на единое серверное время UTC
* Все поля регистрации и создания записей (`created_at`, `verified_at` и др.) переводятся на тип данных `TIMESTAMP WITH TIME ZONE` (`timestamptz`).
* При вставке и обновлении данных сервер СУБД автоматически нормализует временные метки к часовому поясу UTC.

---

### 2. МОДУЛЬ ВЕРИФИКАЦИИ И АВТОМАТИЧЕСКОГО ИНКРЕМЕНТА (`code`)

Поле `code` в системе интерпретируется как **координата состояния системы** (необратимый аналог системного времени / порядковый номер операции).

#### 2.1 Логика расчета и «Предохранитель» (Вариант А)
* **Стартовая точка:** Расчет инкремента всегда начинается динамически от текущей исторической точки: `MAX(code) + 1` на основе уже опубликованных записей в целевой таблице `transactions`.
* **Область действия:** Автоматический расчет выполняется **строго** для записей, находящихся в статусе `need_review` (связка по UUID с таблицей `dicts.dict_statuses`), у которых поле `code IS NULL`.
* **Алгоритм упорядочивания:** Очередь сортируется по физическому времени совершения транзакции: `operation_date ASC, operation_time ASC`.
* **Механизм «Предохранителя» (Строгая точность):** 
  Если две или более транзакции претендуют на одну и ту же координату (имеют идентичные `operation_date` и `operation_time`) или если эти параметры не заполнены, система **немедленно останавливает расчет** на последнем устойчивом порядковом номере. 
  * Сбойная запись и вся последующая за ней очередь остаются в статусе `need_review` с незаполненным полем `code`.
  * Дальнейшая обработка блокируется до ручного распределения координат оператором.

#### 2.2 Интерфейс управления координатами
На панели модератора («Review») должны быть реализованы следующие элементы:
1. **Поле ручного ввода:** Возможность оператора вручную записать/откорректировать значение `code` для спорных транзакций в таблице `staging_transactions`. Без заполненного `code` публикация записи физически невозможна.
2. **Кнопка пересчета инкремента:** Инициирует повторный запуск функции автоматического расчета по оставшейся очереди `need_review` с сохранением логики «предохранителя».

---

### 3. ПУЛЬТ УПРАВЛЕНИЯ И АВТОМАТИЧЕСКИЙ КАСКАД ФУНКЦИЙ

Публикация данных из буфера `staging_transactions` в основной регистр `transactions` является **строго контролируемой операцией** и выполняется только по прямой команде оператора через пульт управления.

#### 3.1 Сценарий публикации и оркестрации
В момент одобрения пачки данных оператором система последовательно и транзакционно выполняет следующий каскад функций:

1. **Публикация:** 
   ```sql
   SELECT audit.post_reviewed_transactions();
   ```
   *Перенос проверенных строк с присвоенными `code` в основную таблицу. Статус записей в staging меняется на `posted`.*

2. **Обновление регистра:**
   ```sql
   SELECT public.refresh_ledger();
   ```
   *Пересчет главной книги (Ledger) на основе новых транзакций.*

3. **Обновление отчета состояний и автоматический аудит:**
   ```sql
   SELECT public.refresh_account_state_report();
   ```
   *Актуализация балансов, расчет статусов счетов и автоматическая запись финансового снимка системы в лог.*

4. **Генерация превью (Контрольный срез):**
   ```sql
   SELECT * FROM reports.v_active_account_report;
   ```
   *Вывод актуального состояния счетов для визуального контроля оператором.*

---

### 4. КОНТРОЛЬ ЦЕЛОСТНОСТИ (`reports.system_verification_log`)

Запись в лог верификации осуществляется автоматически внутри процедуры `public.refresh_account_state_report()`. Лог фиксирует состояние системы при каждой процедуре обновления отчета.

#### 4.1 Изменения в логике работы лога (Модификация существующей функции)
1. **Устранение жесткого барьера:** Запись в `reports.system_verification_log` должна создаваться при любом исходе сверки. Если балансы сошлись, выставляется статус `SUCCESS`. Если обнаружены расхождения, система фиксирует состояние под кодом `WARNING_MISMATCH`, обеспечивая непрерывную историю аудита.
2. **Динамический хэш:** Для предотвращения коллизий ограничений `UNIQUE (verification_hash)` при частых ручных или автоматических пересчетах, алгоритм генерации MD5-хэша дополняется подмешиванием текущего серверного времени высокой точности (`clock_timestamp()`).
3. **Рефакторинг типов функций:** Внутренняя выборка, сопоставление данных с `dicts.accounts` и агрегация массива `verified_account_ids` полностью переводятся с текстовых идентификаторов на строгое сопоставление по `UUID`.

---

### 5. СТРУКТУРА НЕОБХОДИМЫХ ТАБЛИЦ ДЛЯ КОНТРОЛЯ РЕЗУЛЬТАТОВ

#### 5.1 Таблица отчета состояний счетов
```sql
CREATE TABLE reports.account_state_report (
    account_id uuid NOT NULL, -- Переведено на UUID
    account_name varchar(100) NULL,
    entity varchar(100) NULL,
    balance numeric(19, 4) NULL,
    account_balance_status varchar(50) NULL,
    last_updated timestamptz DEFAULT CURRENT_TIMESTAMP NULL, -- Переведено на UTC
    account_state varchar(20) NULL,
    snapshot_tr_id int4 NULL, -- Координата состояния (вводится оператором)
    acc_last_tr_id int4 NULL, -- Последний системный code транзакции
    acc_balance_snapshot_balance numeric(19, 4) NULL,
    CONSTRAINT account_state_report_pkey PRIMARY KEY (account_id)
);
```

#### 5.2 Таблица лога верификации системы
```sql
CREATE TABLE reports.system_verification_log (
    id uuid DEFAULT gen_random_uuid() NOT NULL,
    verified_at timestamptz DEFAULT CURRENT_TIMESTAMP NULL, -- Переведено на UTC
    status_id uuid NOT NULL,
    total_accounts_processed int4 NOT NULL,
    verified_count int4 NOT NULL,
    total_balance_sum numeric(19, 4) NOT NULL,
    verified_account_ids _uuid NOT NULL, -- Массив UUID затронутых счетов
    verification_hash varchar(64) NOT NULL,
    CONSTRAINT system_verification_log_pkey PRIMARY KEY (id),
    CONSTRAINT fk_verification_log_status FOREIGN KEY (status_id) REFERENCES dicts.dict_statuses(id),
    CONSTRAINT uq_verification_hash UNIQUE (verification_hash)
);
CREATE INDEX idx_sys_verification_log_date ON reports.system_verification_log USING btree (verified_at);
```
