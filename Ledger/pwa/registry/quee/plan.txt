План работ по модернизации транзакционного шлюза и модуля верификации
Этап 1. Подготовка схемы данных и миграции (Database Schema & Types)
Цель: Перевод таблиц и связанных сущностей на uuid и timestamptz, подготовка структуры под новые требования.

Миграция типов полей и внешних ключей:

Конвертация полей со строковым хранением внешних ключей (_str) в тип UUID в audit.staging_transactions.

Синхронный перевод связанных полей (включая reports.account_state_report.account_id) на тип UUID с пересозданием внешних ключей и индексов.

Переход на UTC:

Изменение типов колонок времени (created_at, verified_at, last_updated и др.) на TIMESTAMP WITH TIME ZONE (timestamptz).

Настройка параметров сессии СУБД для работы в часовом поясе UTC.

Обновление таблиц отчетов и логов:

Приведение структуры reports.account_state_report и reports.system_verification_log в соответствие с п. 5 ТЗ (включая массив затронутых счетов _uuid и уникальный uq_verification_hash).

Этап 2. Реализация модуля верификации и автоматического инкремента (code)
Цель: Разработка логики расчета координат состояния системы в PL/pgSQL с учетом «предохранителя».

Динамический расчет стартовой точки:

Реализация логики определения начального инкремента на основе MAX(code) + 1 из опубликованных записей transactions.

Алгоритм упорядочивания и «Предохранитель»:

Фильтрация записей в статусе need_review с code IS NULL.

Сортировка по operation_date ASC, operation_time ASC.

Проверка на коллизии (дублирование operation_date и operation_time у разных транзакций или незаполненные поля).

Реализация остановки расчета на последнем устойчивом номере при срабатывании предохранителя (оставшаяся очередь остается в need_review без code).

Этап 3. Пульт управления и каскад функций (Backend & Reflex Integration)
Цель: Интеграция базы данных с Python/Reflex-интерфейсом и оркестрация публикации.

Разработка эндпоинтов / бизнес-логики на Python:

Реализация функций вызова каскада на стороне бэкенда:

SQL
SELECT audit.post_reviewed_transactions();
SELECT public.refresh_ledger();
SELECT public.refresh_account_state_report();
SELECT * FROM reports.v_active_account_report;
Интерфейс модератора («Review») в Reflex:

Создание UI-элементов для отображения спорных транзакций.

Поле ручного ввода/корректировки значения code для записей в staging_transactions.

Кнопка повторного запуска автоматического расчета инкремента («Пересчитать инкремент»).

Блокировка кнопки публикации до заполнения всех обязательных code.

Этап 4. Рефакторинг логики контроля целостности (Лог верификации)
Цель: Доработка процедур аудита и логирования.

Смягчение барьера логирования:

Модификация public.refresh_account_state_report() для обязательной записи в reports.system_verification_log при любом исходе (SUCCESS при сшедшихся балансах, WARNING_MISMATCH при обнаружении расхождений).

Динамический хэш (verification_hash):

Добавление clock_timestamp() в алгоритм формирования MD5-хэша для избежания коллизий уникальности при частых пересчетах.

Строгая типизация UUID:

Перевод внутренних выборок, сверки с dicts.accounts и агрегации массива verified_account_ids на чистый UUID.

Этап 5. Тестирование и верификация (Testing & QA)
Цель: Проверка корректности работы всей цепочки на имеющихся тестах.

Интеграционные тесты:

Запуск существующих тестов для проверки корректности расчета code, срабатывания «предохранителя» при коллизиях времени.

Проверка корректности отображения account_state в account_state_report.

Проверка каскада:

Тестирование транзакционного выполнения цепочки от публикации в staging до генерации превью через Reflex.
