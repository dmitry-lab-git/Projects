# Техническое задание: Система обработки чеков и создания транзакций

## 1. Общие сведения
Цель: Создание потока обработки данных, при котором оцифрованные чеки (статус `NEW`) проходят проверку и превращаются в записи в таблице `audit.staging_transactions`, с последующей миграцией в основную таблицу `transactions`.

## 2. Frontend (Верстка и логика интерфейса)

### А. Страница "Новые чеки" (`/checks/new`)
* **Отображение:** Таблица со списком чеков, где `status = 'NEW'`.
* **Функционал:**
    * Фильтр по статусу (по умолчанию `NEW`).
    * Клик по строке: переход на форму создания транзакции с передачей `receipt_id`.
* **Финишное состояние:** Если список пуст, отображается сообщение: "Все чеки проработаны".

### Б. Форма создания транзакции
* **Pre-fill:** Поля формы автоматически заполняются данными из чека (`amount`, `operation_date`, `operation_time`, `legal_entity_bin_iin`).
* **Валидация контрагента:**
    * Система проверяет наличие `contragent_id`.
    * Если `contragent_id` не найден: блокировать кнопку "Записать в базу данных", вывести предупреждение и предложить ссылку на создание нового контрагента.
* **Действия:**
    * При нажатии "Записать в базу данных" — отправка `POST` запроса на бэкенд.
    * При успехе: автоматический редирект на `/checks/new`.

## 3. Backend (API и логика)

### А. API Endpoints
1. `GET /api/receipts?status=NEW` — получение списка чеков для обработки.
2. `POST /api/transactions/create` — создание транзакции на основе данных чека.

### Б. Логика обработки (Atomicity)
При получении запроса на создание транзакции система выполняет действия в рамках одной SQL-транзакции:
1. **Валидация:** Проверка всех обязательных полей и существования контрагента.
2. **Вставка данных:** `INSERT INTO audit.staging_transactions (...)` (с привязкой `source_extraction_id`).
3. **Обновление статуса:** `UPDATE receipts SET status = 'PROCESSED' WHERE id = :receipt_id;`
4. **Откат:** Если `INSERT` в `staging_transactions` не удался, статус в `receipts` остается `NEW`.

## 4. База данных и структура

* **Таблица `audit.staging_transactions`:** (согласно модели SQLAlchemy).
* **Таблица `receipts`:**
    * Поле `status` (default: `NEW`).
    * Поле `processed_at` (timestamptz) для аудита.
* **Процедура переноса:** Использование `SELECT audit.post_reviewed_transactions();` для миграции из `staging` в `transactions` после просмотра оператором.
