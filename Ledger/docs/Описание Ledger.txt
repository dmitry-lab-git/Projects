ТЕХНИЧЕСКАЯ ДОКУМЕНТАЦИЯ: ИНФРАСТРУКТУРА ВАЛИДАЦИИ TRANSACTIONS_POSTING
================================================================================

1. ОБЩАЯ АРХИТЕКТУРА
--------------------------------------------------------------------------------
Система переходит от жестко закодированной логики к графовой модели валидации.
Функция transactions_posting(jsonb) выступает как оркестратор, использующий
таблицы nodes (сущности) и edges (правила/связи) для проверки допустимости
транзакции до её фиксации.

2. КОМПОНЕНТЫ СИСТЕМЫ
--------------------------------------------------------------------------------
- TRANSACTION_POSTING: Исполнительная функция для одиночных транзакций.
- TRANSACTIONS_BATCH_POSTING: Функция-обертка для пакетной обработки,
  использующая transaction_posting как атомарный элемент.
- NODES / EDGES: Графовая структура, определяющая допустимые финансовые связи,
  типы операций и ограничения контрагентов.
- ERROR_POSTING_LOG: Таблица аудита, содержащая полный отчет о причинах отказа.
  Обеспечивает пользователя алгоритмической поддержкой для исправления данных.

3. ПРИНЦИПЫ РАБОТЫ (ВАЛИДАЦИЯ)
--------------------------------------------------------------------------------
- Атомарность: Вставка транзакции происходит только при полном прохождении
  валидации по графу правил.
- Блокировка: Любое нарушение (хронология, валюта, контрагенты, логические
  связи в графе) приводит к ROLLBACK транзакции.
- Информативность: Вместо одиночной ошибки функция возвращает развернутый
  аудит-отчет, позволяющий пользователю понять все узкие места в запросе.

4. ЖИЗНЕННЫЙ ЦИКЛ ОШИБОК
--------------------------------------------------------------------------------
Система не оставляет пользователя без поддержки. В случае отказа генерируется
аудиторский лог, описывающий:
- Нарушенное бизнес-правило (из таблицы edges).
- Контекст ошибки (ID транзакции, текущее состояние счета, хронологический
  разрыв).
- Рекомендации по приведению транзакции в валидное состояние.

5. СТРАТЕГИЯ МАСШТАБИРОВАНИЯ
--------------------------------------------------------------------------------
- Разделение ответственности: transaction_posting для высокоточных одиночных
  операций, transactions_batch_posting для массовых импортов.
- Гибкость: Добавление нового финансового правила требует записи в таблицу
  edges, а не изменения программного кода базы данных.

6. ЦЕЛЬ ИНФРАСТРУКТУРЫ
--------------------------------------------------------------------------------
Создание саморегулируемой среды, где математическая точность (Ledger/Snapshot)
подкреплена строгой логической моделью (Граф правил), исключающей ввод
корректировок задним числом и нарушение хронологической целостности.
================================================================================

ТЕХНИЧЕСКАЯ ДОКУМЕНТАЦИЯ: АНАЛИЗ СВЯЗЕЙ И СТРУКТУРЫ ДАННЫХ
================================================================================

1. СТРУКТУРА ТРАНЗАКЦИИ (FIELDS)
--------------------------------------------------------------------------------
Для реализации графовой модели валидации, каждое поле таблицы transactions
будет являться узлом (node) или ребром (edge) в нашей системе:

- id (UUID): Уникальный идентификатор узла транзакции.
- code (INT): Порядковый номер (хронологический маркер).
- parent_id (UUID): Ссылка на родительский узел (иерархия транзакций).
- transaction_name (VARCHAR): Описание узла.
- amount (NUMERIC): Атрибут (вес) операции.
- currency_id (UUID): Ссылка на узел валюты.
- operation_date/time: Временные метки (хронологический вектор).
- registration_date/created_at: Системные метаданные.
- type_id (UUID): Тип операции (ключевой узел для ветвления графа).
- entity_id (UUID): Сущность (актив/центр ответственности).
- category_id (UUID): Классификатор (связь с группирующим узлом).
- responsible_id (UUID): Ответственное лицо.
- contragent_from_id (UUID): Узел-источник средств.
- contragent_to_id (UUID): Узел-получатель средств.
- account_id (UUID): Целевой узел счета (основной аккаунт).
- source_extraction_id (UUID): Ссылка на узел-источник данных (импорт).
- tx_hash (VARCHAR): Маркер уникальности.
- status (VARCHAR): Статус узла (NEED_REVIEW -> VERIFIED).

2. КАТАЛОГ БИЗНЕС-ПРАВИЛ (EDGES & NODES MAPPING)
--------------------------------------------------------------------------------
На основе анализа выявлены следующие жесткие связи (edges):

A. ДОХОД:
   - contragent_to = 'CNA-056' (Баланс).

B. РАСХОД:
   - contragent_from = 'CNA-056' (Баланс).
   - contragent_to != 'CNA-056' (Запрет на возврат на балансовый счет).

C. РЕВИЗИЯ:
   - contragent_from = 'CNA-056'.
   - contragent_to = 'CNA-056'.
   - category_id = 'CAT-028'.
   - entity_id = 'ENT-020'.

D. ПЕРЕНОС:
   - contragent_from = 'CNA-056'.
   - contragent_to = 'CNA-056'.
   - category_id = 'CAT-030'.
   - entity_id = 'ENT-040'.

E. КОРРЕКТИРОВКА:
   - contragent_from = 'CNA-056'.
   - contragent_to = 'CNA-056'.
   - category_id = 'CAT-028'.
   - entity_id = 'ENT-020'.

3. АНАЛИТИЧЕСКИЕ ЗАМЕТКИ О СВЯЗЯХ
--------------------------------------------------------------------------------
- Узел 'CNA-056' (Баланс) является системным узлом-якорем. Почти все 
  некоммерческие операции (Ревизия, Перенос, Корректировка) замыкаются на нем.
- Существует строгая зависимость: Тип операции (type_id) жестко детерминирует 
  допустимый набор связей (edges) между контрагентами и категориями.
- Поле 'entity_id' является потенциальным расширением графа (связи между 
  сущностями, например: растение -> Google). Для MVP мы сохраняем его как 
  атрибут, но архитектурно готовим к выносу в отдельный граф связей.
- Отсутствие 'snapshot' для 'account_id' является критическим блокирующим 
  состоянием. Это связь второго порядка: транзакция не может существовать 
  без доказательства состояния счета в прошлом.
